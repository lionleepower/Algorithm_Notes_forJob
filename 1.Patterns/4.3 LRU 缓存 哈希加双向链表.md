# 146. LRU 缓存：设计题的标准答法

## 题目

设计一个容量为 `capacity` 的缓存，`get(key)` 和 `put(key, value)` 都要求 $O(1)$。
容量满时淘汰**最久未使用**（Least Recently Used）的键。

## 思路

这是最高频的**设计题**，考的不是算法而是**「用两个结构互补，各自补上对方的短板」**这个意识。

先把需求拆成三个 $O(1)$：

```text
1. 按 key 找到节点            -> 哈希表天生 O(1)
2. 把任意节点移到「最新」一端  -> 需要 O(1) 摘除 + O(1) 插入
3. 找到并删除「最旧」的那个    -> 需要一个固定的「最旧」端
```

> [!tip]- 核心思路：为什么必须是「哈希表 + 双向链表」
>
> **单独用哈希表不行**：`dict` 能 $O(1)$ 定位，但**记不住顺序**，不知道谁最久没用。
>
> **单独用链表不行**：链表能记顺序，但按 `key` 查找是 $O(n)$。
>
> **为什么链表必须是双向的**——这是面试官真正想听的一句：
> 摘除一个节点 `x` 需要修改它的**前驱**的 `next`。单向链表拿不到前驱，只能从头遍历，退化成 $O(n)$；双向链表里 `x.prev` 直接可得，摘除就是两行指针改写。
>
> $$\text{哈希表补链表的「查找慢」，链表补哈希表的「无顺序」}$$
>
> **约定一个方向并写死**（本篇：靠近 `head` 是最新，靠近 `tail` 是最旧）。方向本身无所谓，**中途改主意才是 bug 之源**。
>
> **哨兵头尾（dummy head / dummy tail）**：真实节点永远夹在两个哨兵之间，于是「插到头部」「删掉尾部」都不必判断空表、单元素、首尾节点等特例——链表永远「有前有后」。这与 [[4.2 删除链表]] 里 dummy 消除头结点分支、[[2.3 栈 括号匹配与表达式解码]] 里 `min_st` 的 `inf` 哨兵，是同一个技巧的三次出现。

> [!example]- 示例推演：`capacity = 2`
>
> ```text
> put(1,1)   head <-> [1] <-> tail                      cache={1}
> put(2,2)   head <-> [2] <-> [1] <-> tail              cache={1,2}
> get(1)     命中 -> 把 1 移到头部
>            head <-> [1] <-> [2] <-> tail              返回 1
> put(3,3)   满了 -> 删尾部（最旧 = 2）
>            head <-> [3] <-> [1] <-> tail              cache={1,3}
> get(2)     未命中 -> 返回 -1
> ```
>
> 注意 `get(1)` **也会改变顺序**——「使用」包括读，这是最常被漏掉的一条。

## 代码实现

> [!success]- 手写双向链表版（面试必须能默写这一版）
>
> ```python
> class Node:
>     __slots__ = 'key', 'val', 'prev', 'next'
>     def __init__(self, key=0, val=0):
>         self.key, self.val = key, val
>         self.prev = self.next = None
>
> class LRUCache:
>     def __init__(self, capacity: int):
>         self.cap = capacity
>         self.cache = {}                       # key -> Node
>         self.head = Node()                    # 哨兵头：靠近它 = 最新
>         self.tail = Node()                    # 哨兵尾：靠近它 = 最旧
>         self.head.next = self.tail
>         self.tail.prev = self.head
>
>     # ---- 两个私有原语，所有操作都由它们拼出来 ----
>     def _remove(self, node: Node) -> None:
>         node.prev.next = node.next
>         node.next.prev = node.prev
>
>     def _add_front(self, node: Node) -> None:
>         node.next = self.head.next
>         node.prev = self.head
>         self.head.next.prev = node
>         self.head.next = node
>
>     def get(self, key: int) -> int:
>         if key not in self.cache:
>             return -1
>         node = self.cache[key]
>         self._remove(node)                    # 读也算「使用」
>         self._add_front(node)
>         return node.val
>
>     def put(self, key: int, value: int) -> None:
>         if key in self.cache:                 # 已存在：改值 + 提到最前
>             node = self.cache[key]
>             node.val = value
>             self._remove(node)
>             self._add_front(node)
>             return
>         if len(self.cache) == self.cap:       # 满了：先淘汰最旧
>             lru = self.tail.prev
>             self._remove(lru)
>             del self.cache[lru.key]           # 靠 node.key 反查，所以节点必须存 key
>         node = Node(key, value)
>         self.cache[key] = node
>         self._add_front(node)
> ```
>
> **主流程**：一切操作都归约为 `_remove` + `_add_front` 两个原语。
>
> **关键变量**
> - `cache[key] -> Node`：$O(1)$ 定位
> - `head.next`：最新；`tail.prev`：最旧
> - `Node.key`：**淘汰时用来反查字典**，只存 `val` 会导致字典删不掉
>
> **易错位置**：`_add_front` 的四行指针赋值有顺序依赖——**先接新节点的两侧，再改原有节点的指向**，否则 `self.head.next` 已被覆盖，找不回原来的第一个节点。

> [!success]- `OrderedDict` 速成版（可以写，但必须先讲原理）
>
> ```python
> from collections import OrderedDict
>
> class LRUCache(OrderedDict):
>     def __init__(self, capacity: int):
>         super().__init__()
>         self.cap = capacity
>
>     def get(self, key: int) -> int:
>         if key not in self:
>             return -1
>         self.move_to_end(key)              # 尾部 = 最新
>         return self[key]
>
>     def put(self, key: int, value: int) -> None:
>         if key in self:
>             self.move_to_end(key)
>         self[key] = value
>         if len(self) > self.cap:
>             self.popitem(last=False)       # 弹出头部 = 最旧
> ```
>
> `OrderedDict` 内部**正是哈希表 + 双向链表**。直接上这一版而讲不出原理，面试官会认为你只是背了 API——**先说结构，再说「标准库已经封装好了」**，顺序不能反。
> 当然，我们也可以考虑其他的标准库：
>```python
class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        # from collections import OrderedDict
        # OrderedDict = dict + 双向链表
        self.cache = OrderedDict()  # key -> value
    def get(self, key: int) -> int:
        if key not in self.cache:  # 没有这本书
            return -1
        # 有这本书，把这本书抽出来，放到最上面（last=False 表示移到链表头）
        self.cache.move_to_end(key, last=False)
        return self.cache[key]
    def put(self, key: int, value: int) -> None:
        self.cache[key] = value  # 添加 key value 或者更新 value
        # 把这本书抽出来，放到最上面（last=False 表示移到链表头）
        self.cache.move_to_end(key, last=False)
        if len(self.cache) > self.capacity:  # 书太多了
            self.cache.popitem()  # 去掉最后一本书
>```

## 易错点

> [!warning]- 易错点
>
> **1. `get` 不更新顺序**
> LRU 的「使用」包含读和写。只在 `put` 里更新，会在「读了很久的热键却被淘汰」时错。
>
> **2. 节点里不存 `key`**
> 淘汰尾节点时需要 `del self.cache[lru.key]`。只存 `val` 就无法反查，字典会残留死键、`len` 永远等于容量、之后每次 `put` 都误删。**这是本题最隐蔽的 bug。**
>
> **3. `put` 已存在的 key 时又插了一个新节点**
> 必须走「改值 + 提前」分支。否则同一个 key 在链表里出现两次，字典只指向其中一个，另一个永远删不掉。
>
> **4. 用单向链表**
> 摘除需要前驱，`get` 退化成 $O(n)$。面试官问「为什么双向」时答不上来，等于没做出来。
>
> **5. 不用哨兵**
> 空表 / 只剩一个节点 / 删的正好是头或尾——四种特例，指针判断量翻三倍。**哨兵是这道题最省事的一步。**
>
> **6. 先插入再判容量，或判容量用了 `>`**
> 本文写法是**先淘汰再插入**（`len(self.cache) $==$ self.cap` 时淘汰）。若改成先插入后检查，条件必须是 `len(self.cache) > self.cap`。两种都对，但混着写会差一个。
>
> **7. `capacity = 0`**
> 极端用例：容量为 0 时任何 `put` 都应立刻淘汰刚插入的项。本文写法在 `len == 0 == cap` 时会去删 `tail.prev`（即哨兵头），**需要额外判断**，面试可以主动提一句。
>
> **8. 追问 LFU（460）**
> LFU 按**使用频次**淘汰，同频次内再按 LRU。做法是「频次 $\to$ 一条 LRU 链表」的字典，外加一个 `min_freq`。能说出这个结构就够了。

## 复杂度

> [!summary]- 复杂度
>
> - 时间：`get` / `put` 均为 $O(1)$ —— 哈希查找 $O(1)$，链表摘除与头插各是常数次指针改写，与元素个数无关。
> - 空间：$O(\text{capacity})$ —— 字典与链表各存一份指向同一批节点的引用，节点总数不超过容量。
>
> 对比「只用数组 + 每次线性找最旧」的 $O(n)$：省下的正是「扫描找最旧」这一步，而双向链表用 `tail.prev` 把它变成了 $O(1)$。

## 一句话总结

LRU = **哈希表管「找得到」+ 双向链表管「排得出」**；链表必须双向，是因为 $O(1)$ 摘除需要前驱；哨兵头尾则把所有边界特例一次性消灭。

## 模板归纳

**触发信号 $\to$ 条件反射**

- 「设计一个 X，所有操作 $O(1)$」$\to$ 先问：**哪个操作单靠一个结构做不到？** 缺什么补什么
- 「需要按 key 查 + 需要维护顺序」$\to$ 哈希表 + 双向链表
- 「需要按 key 查 + 需要随机取一个」$\to$ 哈希表 + 数组（380，删除时用「与末尾交换」）
- 「需要按 key 查 + 需要取最值」$\to$ 哈希表 + 堆（见 [[10.0 堆 TopK与对顶堆]]）

**设计题落笔四步**

1. 把每个 API 的复杂度要求单独列出来，逐个问「靠什么结构达成」。
2. 选好结构后**先写两个私有原语**（本题的 `_remove` / `_add_front`），公开方法只负责组合它们。
3. 加哨兵，消掉所有空表与首尾特例。
4. 检查**两个结构的一致性**：字典里有的，链表里必须有；链表删了的，字典必须同步删——**双向可反查**（节点存 `key`）是保证这一点的前提。
